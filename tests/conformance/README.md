# OpenID conformance suite

The suite runs locally from the prebuilt images of `registry.gitlab.com/openid/conformance-suite`, under the `conformance` profile of the root `compose.yaml`:

```bash
castor start --conformance     # OP on https://op.localhost, suite on https://localhost:8443
castor conformance             # every plan; --plan fapi-ciba-poll for one (repeatable), --module oidcc-server for one module (repeatable, substring)
castor conformance --strict    # a WARNING fails too, which is what "conformance.yml" runs
castor logs conformance-server
```

`server-entrypoint.sh` replaces the entrypoint of the suite image for one reason: before starting the suite exactly as the upstream image does, it makes the JVM trust two certificates. The root of the certificate the OP serves (the mkcert root of the machine when `castor start` found one, the internal CA of Caddy otherwise, published by the op container at `/data/beffroi/root.crt`), so that the suite calls `https://op.localhost` like a browser does; and the self-signed certificate of the suite's own nginx, because the scripted browser of the suite runs inside that JVM and follows the redirect of the OP to `https://localhost:8443/test/a/beffroi/callback`. Inside the container, `localhost` is the container: the `conformance-redirector` sidecar of `compose.yaml` shares its network namespace and forwards the loopback port 8443 to nginx (the suite does the same with `fintechlabs.startredir` and a `redir` binary the prebuilt image does not ship).

The suite version is pinned (`CONFORMANCE_SUITE_VERSION`, `CONFORMANCE_NGINX_VERSION` in `compose.yaml`). Certification results must name the version they were produced with; `castor conformance` prints it with the summary.

## The certification plans

Fourteen runs of eleven plans and one module on its own, all named in `CONFORMANCE_PLANS`: `oidcc-basic-certification-test-plan` (spike 1), `oidcc-config-certification-test-plan`, `oidcc-formpost-basic-certification-test-plan`, `oidcc-rp-initiated-logout-certification-test-plan`, `oidcc-frontchannel-rp-initiated-logout-certification-test-plan` and `oidcc-backchannel-rp-initiated-logout-certification-test-plan` (spike 4), the two FAPI 2 plans in their four runs (spike 5), `fapi-ciba-id1-test-plan` in its two runs (spike 6), `oidcc-dynamic-certification-test-plan` and `oidcc-3rdparty-init-login-certification-test-plan` (spike 7), and `oidcc-server-rotate-keys` (spike 2), created without a plan through `/api/runner` since the suite has no plan for a single module; the task rotates the signing key of the OP (`beffroi:keys:rotate --now`) between the creation of that module and its start, where the suite expects the operator to, inside the Dynamic OP plan that carries it as well as in the run of its own. One configuration serves them all; `castor conformance` runs them one after the other, `--plan` picks one.

`oidcc-basic-certification-test-plan` is created with the variants `server_metadata=discovery` and `client_registration=static_client`. The plan is a fixed list of modules, each with its own variant: every one runs with `client_auth_type=client_secret_basic` except `oidcc-server-client-secret-post`, and all with `response_type=code`, `response_mode=default`. Three registered clients serve them: `client` and `client2` (`client_secret_basic`, the second one is the wrong client of some modules) and `client_secret_post` (the one module that authenticates that way). The OP registers them in `apps/op/config/packages/beffroi.yaml` as `conformance-basic`, `conformance-basic-second` and `conformance-post`, with the alias `beffroi` in their redirect URIs (`https://localhost:8443/test/a/beffroi/callback`) and `requires_pkce: false`, because the profile sends no `code_challenge` (decision 0008 of the design repository); `castor provision` generates their secrets into `apps/op/.env.local`.

`oidcc-formpost-basic-certification-test-plan` is created with the same variants and served by the same three clients: it is the Basic OP plan run with `response_mode=form_post`, where the OP answers with a self-submitting page instead of a redirection. The scripted browser needs no entry of its own, the page submits itself and lands on the same callback. Its 35 created modules end in 32 `PASSED` and 3 `REVIEW` since spike 5 brought request objects (beffroi#161): `oidcc-unsigned-request-object-supported-correctly-or-rejected-as-unsupported`, which writes `response_mode` only inside the request object, was the one module listed as known, and the `known` list of the plan is now empty. It reads that object because `conformance-basic` registers `request_object_signing_alg: none` (OIDC Registration §2), which no other client of the OP does.

The two logout plans are created with `response_type=code` and `client_registration=static_client`, and each is served by a client of its own, `conformance-front-channel-logout` and `conformance-back-channel-logout`, which register the URI of their channel and of no other: the suite certifies one channel at a time, a client that registers a logout URI is told at every logout of its sessions, and a module of another plan then fails on a request it did not expect. The back-channel plan is the only one whose result depends on the worker, which posts the logout token: the `conformance-worker-redirector` sidecar of `compose.yaml` brings the loopback port 8443 of the suite into the network namespace of the worker, and `docker/worker/entrypoint.sh` adds the self-signed certificate of nginx to the trust store of that container, the way `server-entrypoint.sh` adds it to the truststore of the JVM. A worker that restarts leaves the sidecar forwarding nothing, so whatever restarts the worker creates the sidecar again behind it: restarting the sidecar does not bring it back, it holds the identifier of the namespace it joined when Docker created it.

`fapi2-security-profile-final-test-plan` and `fapi2-message-signing-final-test-plan` are each created twice, once per pair of mechanisms FAPI 2 lets an authorization server choose between (`private_key_jwt` with DPoP, `mtls` with certificate-bound tokens), which makes four runs of the ten; `CONFORMANCE_PLANS` says which variants and `castor provision` which four clients. What they need that the six OpenID Connect plans do not is in `var/conformance/`, written by `castor provision`: one P-256 key per client, private half included since the suite is the client here, and the self-signed certificate of the two that present one. `castor conformance` reads those files and builds the `client`, `client2`, `mtls`, `mtls2` and `resource` sections of the configuration from them, which is why those sections are not in `configuration.json` at all; the client that authenticates with a shared secret has no place in a FAPI run and is taken out of it. Each of the four lists one module under `known`, `fapi2-security-profile-final-test-claims-parameter-identity-claims`, known to end in `WARNING` on the one condition `CheckForUnexpectedClaimsInIdToken` because the suite does not know the `sid` of the ID token, and on nothing else: issue beffroi#210 says why the provider emits the claim and why it keeps it.

`fapi-ciba-id1-test-plan` is created twice, once per delivery mode (`ciba_mode=poll` and `ciba_mode=ping`), with `client_auth_type=private_key_jwt`, `fapi_ciba_profile=plain_fapi` and `client_registration=static_client`. It is the plan of the one flow with no browser of the client in it: four clients serve the two runs, two per run, because a client registers one delivery mode (CIBA Core §4), each holding a P-256 key and a certificate issued on it, both written by `castor provision` into `var/conformance/`. The suite names the user with the `sub` the provider issued, published by the same task as `BEFFROI_DEV_USER_SUBJECT`. Nobody is at a screen, so the configuration carries `automated_ciba_approval_url`, which the suite posts the answer of the user to with the identifier of the request substituted into it; what answers there is `/ciba/conformance/approval`, an endpoint of the bundle the application imports in development only, as it imports the endpoints of the FIDO2 server API. It signs the user in with their password and answers the request with the two calls the approval page answers with. In ping mode the provider posts the identifier of the answered request to the endpoint the suite serves, which the worker reaches through the `conformance-worker-redirector` sidecar and the certificate its entrypoint trusts, exactly as it reaches it for a logout token. The two runs do not pass: the rules of the profile they found are written in the issues `CONFORMANCE_CIBA_ISSUES` names, and `CONFORMANCE_PLANS` names those issues under `waiting_on`, so the runs are reported and do not fail the task while they are open.

`oidcc-dynamic-certification-test-plan` (23 modules) and `oidcc-3rdparty-init-login-certification-test-plan` (2 modules) are the two runs whose clients this provider has never seen. Both plans fix `server_metadata=discovery`, `client_registration=dynamic_client`, the client authentication (`private_key_jwt` for the first, `client_secret_basic` for the second) and `response_mode=default` themselves, so the one variant `CONFORMANCE_PLANS` writes for either is `response_type=code`. The `dynamic_client` variant hides `client.client_secret` and `client.jwks` and reads two things of a client section, the name the client registers under and the initial access token it presents: the suite draws an RS256 key per client and sends it in the registration request, and the open mode of the tenant asks for no token (decision 0009 of the design repository), so `castor conformance` replaces the client sections with a name apiece and takes out the client that authenticates with a shared secret. Nothing is declared in `apps/op/config/packages/beffroi.yaml` for them and `castor provision` draws nothing: what they need of the deployment is the registration policy of the tenant, written under `when@dev`, and the task reads the discovery document for a `registration_endpoint` before it creates either plan rather than letting every module fail on the same line. The suite deletes each client it registered at the end of the module that registered it (RFC 7592 §2.3), and the retention the tenant names catches what a module that stopped earlier left behind. Both runs gate, like the plans of the spikes before them and with no `waiting_on` line: every module of either ends in a result the task accepts, and the eleven of the Dynamic OP plan that the provider does not get past are written one by one under `known`, with the reason and the issue of each.

`--reset` empties the database of the OP, provisions it again, restarts the containers and waits for the discovery document. The plans want the OP as `castor provision` leaves it, a development user with a password and nothing else: a second factor or a passkey enrolled by hand stops the scripted browser on the page that asks for it, and every module of every plan then fails on `unexpected url for task: Verify complete`. Only one run at a time, whatever the plan: the alias of the configuration is exclusive, and two runs at once interrupt each other.

`configuration.json` is the configuration of every plan. It carries no secret: `castor conformance` fills its `{PLACEHOLDERS}` from the environment of the application (`BEFFROI_ISSUER`, the five `CONFORMANCE_*_SECRET`, `BEFFROI_DEV_USER_PASSWORD`) and from the development user (`BEFFROI_DEV_USERNAME`), then creates each plan through the API of the suite, runs its modules one after the other (the alias makes them exclusive) and prints the result of each with the failures and warnings of its log, then a summary and the URL of each plan. The exit code is 1 when a module is `FAILED`, `INTERRUPTED` or `TIMEOUT`, unless its plan lists it under `known`, where a gap is written down whole: the result the module is known to end in, the findings that result is made of, and the reason with the issue that closes it. It is reported as `KNOWN` and accepted only when the run is exactly that gap; a failure where a warning was written down, a finding beside the ones written down, or the module passing, is not that gap, and the run fails on it, so that a regression on a module left open stays visible and the line is deleted rather than carried. The task says, module by module, what was written down and what came instead. `WARNING` and `REVIEW` are for a human to read on the plan page before anything is submitted, `SKIPPED` is the suite's own choice. `--strict` moves `WARNING` to the failing side, which is how `conformance.yml` reads them: a warning is a specification the provider answers less than it should, and it is not a state a submission may be in. `REVIEW` and `SKIPPED` stay accepted under `--strict` as well, no run of a plan can avoid them: twenty modules of the OpenID Connect plans end in `REVIEW` because they ask for a capture of a page of the OP, which the scripted browser fills with the text of that page: three of the Basic OP plan, the same three of the Form Post one, eight of the RP-Initiated Logout one and six of the Dynamic OP one. `oidcc-unsigned-request-object-supported-correctly-or-rejected-as-unsupported` was skipped by the suite itself in the Basic OP plan as long as the OP answered `request_not_supported`, which the profile permits; since beffroi#161 the OP reads the object, the module runs and it passes. `oidcc-ensure-request-object-with-redirect-uri` had an override of its own for the same reason and no longer needs one: it sends an unregistered `redirect_uri` in the query and the registered one inside the request object, so the OP used to refuse on the query before it read the object and showed its error page; it now reads the object, whose parameters are the request (OIDC Core §6.1), and answers a redirection to the registered URI, which the default entry of the `browser` section follows like any other. That object is unsigned, so the same module of the Dynamic OP plan is refused on it, the client that plan registers having registered no `request_object_signing_alg` (decision 0012): a `browser` block is named by module and read by every plan that carries it, so the gap is written under `known` for the plan that has it instead.

The workflow `.github/workflows/conformance.yml` runs all of it, and nothing else does: it is asked for by hand (`gh workflow run conformance.yml`, with the plans, the modules and `--strict` as inputs) and it runs every Monday at 03:17 UTC on the default branch, which is the newest maintenance branch. No push and no pull request pays for it. The stack is started on the runner, `castor provision` writes a fresh `apps/op/.env.local` and restarts the worker so that it holds the secrets just written, and the plans run with `--strict`, which is what a dispatch that names nothing and the schedule both ask for. The run takes twenty-one to twenty-two minutes for the thirteen entries measured on 2026-09-27 (five consecutive runs of the maintenance branch), of which two build the image and start the stack, and the two runs of spike 7 are not in that figure; on a development machine, the Basic OP plan takes 2 min 36, of which `oidcc-codereuse-30seconds` waits out its thirty seconds on its own, the Form Post OP plan 2 min 35, which is the same modules, RP-Initiated Logout 42 s, and each of the two logout channels six seconds. The two FAPI-CIBA runs add nothing measurable while they do not pass: every one of their 35 and 40 modules ends in under a second, stopping at the first refusal (measured on a development machine on 2026-09-26, suite 5.2.1). The runner starts from an empty database on every run, so `--reset` is a developer's option, on a stack that has been used, and the workflow does not offer it. It runs on the host and not in the phpqa image, needing a Docker daemon, and installs the application with its own lock, the way a developer runs it, the monorepo jobs of `ci.yml` being the ones that follow the dev branches of Symfony.

The `browser` section of the configuration drives the scripted browser of the suite (HtmlUnit, see the BrowserControl page of the suite's wiki): on the login page it answers the step of the address with the username, `#address` (beffroi/saml S-61: the development tenant federates a domain to the identity provider of `castor saml-idp`, and a username, of no domain, is sent on to the usual page), then fills `#username` and `#password` and submits, on the consent page it clicks `button[name=answer][value=allow]`, all three optional because a module may find the user signed in or the consent given, then it waits for `#submission_complete` on the callback of the suite. A second entry drives the end session endpoint: it clicks `button[name=confirm][value=yes]` when the OP shows its confirmation page (an optional command, since a verified `id_token_hint` skips the page) and waits for `https://localhost:8443/test/a/beffroi/post_logout_redirect`. The `override` section adapts it for the modules that expect an error page on the OP instead of a redirect (`oidcc-ensure-registered-redirect-uri` of the Basic OP plan, and `oidcc-ensure-redirect-uri-in-authorization-request`, `oidcc-redirect-uri-query-mismatch` and `oidcc-redirect-uri-query-added` of the Dynamic OP one, which send no `redirect_uri` at all, one whose query is not the registered query, and one with a query the registration has not: the text of the page fills the screenshot placeholder of the module, hence a `REVIEW` result) and for those that need a second login (`oidcc-prompt-login`, `oidcc-max-age-1`); the logout modules that end on the OP get theirs too, the signed-out page, the error page or, for `oidcc-rp-initiated-logout-bad-id-token-hint` whose hint the OP cannot verify, the confirmation page filling the placeholder, unanswered. The three modules of the Dynamic OP plan that register a `logo_uri`, a `policy_uri` or a `tos_uri` (`oidcc-registration-logo-uri`, `-policy-uri`, `-tos-uri`) get one apiece for the same reason: this provider shows what a client registered about itself on its consent page (OIDC Registration §2), so the browser signs in, waits for the image or the link the module registered, by the `data-client` attribute that names the member, and the text of that page fills the placeholder. Their flow ends on that page, those modules reading no callback (`AbstractOIDCCDynamicRegistrationTest`: "it is not necessary to complete login for this test"). An override replaces the whole `browser` array, which is why each of them repeats the authorization entry. What fills a placeholder that way is the page the OP served and not a capture: a submission for certification carries screenshots taken by a human, on the plan page of the suite, and what the browser buys is a run that gates instead of one that waits five minutes per module for nobody. A module whose placeholder nothing fills stays `WAITING` and is reported `TIMEOUT`, and a module the browser cannot finish waits for a human: the task prints the URL the suite exposes and waits up to five minutes.

Every run is recorded in the journal of `spikes/01-conformite/README.md` of the documentation repository, with the suite version.

## FIDO Alliance conformance tools

The FIDO Conformance Tools are a desktop application of the FIDO Alliance, obtained on request from fidoalliance.org (its version goes in the journal with every run); nothing of them runs in CI, the run is by hand, like the hosted suite of spike 1. The server tests of FIDO2 drive the four endpoints of the FIDO2 server API (`/attestation/options`, `/attestation/result`, `/assertion/options`, `/assertion/result`), which the bundle provides in `src/symfony/src/Fido/Conformance/` on the enrolment and the authentication of the core, with what the tools ask for and the product never does (the attestation conveyance, the authenticator selection, the extensions), the users created on their first ceremony. The application imports them in development only (`apps/op/config/routes/fido_conformance.yaml`, `when@dev`, the prefix `/fido/conformance`), as it registers the clients of the OpenID suite: they are not an API of the product. The tools are given `https://op.localhost/fido/conformance` as the server URL and append the four paths; they must trust the internal CA of Caddy, or be told not to check the certificate, and reach `op.localhost` (127.0.0.1 on the host that runs the stack).

The tools verify the attestation of their virtual authenticators against metadata, which the ceremonies read from the store of `beffroi.webauthn.metadata_storage` (`/app/var/webauthn` in the op container, the anonymous `var` volume of the container, which `castor start` keeps):

- the metadata statements of the virtual authenticators, shipped by the tools (a directory of JSON files), copied into the container and imported as they are, unsigned: `docker compose cp <directory> op:/tmp/statements` then `castor console beffroi:webauthn:mds-import /tmp/statements/*.json`;
- the MDS3 tests, whose blobs the tools serve from endpoints they list for the server URL given, signed under a test root: `castor console beffroi:webauthn:mds-refresh --root https://mds3.certinfra.fidoalliance.org/pki/MDS3ROOT.crt --url <endpoint>` with every endpoint listed (`--url` is repeatable); a blob the tools sign badly on purpose is refused and printed as such, which is what those tests check;
- the real metadata service, for a run against real authenticators: `castor console beffroi:webauthn:mds-refresh` alone downloads the blob of the FIDO Alliance (`https://mds.fidoalliance.org/`, which `https://mds3.fidoalliance.org/` redirects to; no outbound request follows a redirect) and verifies it under the GlobalSign Root CA - R3 the bundle ships. The service rate-limits: a refresh is a by-hand act, one per day at most.

A document of the store is read once per process (the workers of FrankenPHP restart on a source change, not on a write under `var/`): restart the stack after a refresh or an import, or the running workers keep what they read.

Which tests pass, which are skipped and why, go in the journal of `spikes/03-passkeys/README.md` of the documentation repository, with the version of the tools and the date, as the runs of the OpenID suite go in the journal of spike 1.
